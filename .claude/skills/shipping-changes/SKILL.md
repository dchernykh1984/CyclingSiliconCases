# Как выкатывать изменения

## Ветка от свежего main

Всегда от обновлённого `main` (`git checkout main && git pull`). Имя — по сути
правки: `feat/engrave-830`, `fix/840-back-wall`, `chore/project-setup`.

## Коммиты

- **Одна атомарная правка — один коммит.** Задача, замечание, фикс — каждый
  отдельно. Если работа разошлась на «модель», «каталог» и «документацию»,
  это три коммита.
- **Одна строка, без тела.** Никаких `Co-Authored-By` и упоминаний Claude.
  Хук в `.claude/settings.json` блокирует такой коммит.
- Типы conventional commits: `feat`, `fix`, `docs`, `chore`, `ci`, `perf`,
  `refactor`, `test`, `build`, `style`. От типа зависит версия, которую
  поставит release-please: `feat` двигает минорную, `fix` — патч.
  **`chore` и `ci` не двигают ничего** — если в ветке только они, релиза
  не будет.
- Пишите, что изменение даёт читателю: `feat: engrave the owner name on the
  830 case`, а не «правки в cases.py».
- pre-commit может переформатировать файл и уронить коммит — повторите ту же
  команду `git commit`, второй раз пройдёт.

Файлы добавляйте прицельно (`git add <файлы>`): в рабочем дереве почти
всегда лежат собранные `dist/` и `preview/`.

## Пулл-реквест

`gh pr create` с телом, где сказано, что поменялось и почему именно так.

**Подписи инструмента в тело PR не идут.** Ни «Generated with…», ни
упоминания Claude, ни соавторства — то же правило, что и для коммитов,
и по той же причине: работа идёт от имени автора репозитория. Это
относится и к описаниям релизов, и к комментариям в PR.
Для геометрии — с цифрами: какой отступ остался, что упёрлось в кромку,
почему выбран такой размер. Решение, принятое из-за геометрии, пишется
в тело PR, а не остаётся в голове.

Дальше:

1. `gh pr checks <N>` — дождаться всех пяти проверок: `Lint & types`,
   `Tests (py3.11|3.12|3.13)`, `Build cases`.
2. Мержить `gh pr merge <N> --rebase --admin --delete-branch`.

## Релиз

Релизы делает [release-please](https://github.com/googleapis/release-please):
после мержа в `main` он открывает PR вида `chore(main): release 0.1.0`
с обновлённым `CHANGELOG.md`, `.release-please-manifest.json` и строкой версии
в `src/cycling_cases/__init__.py` (там стоит маркер `x-release-please-version`).

Выпуск:

1. `gh pr merge <N> --rebase --admin`;
2. workflow `Release` собирает чехлы и прикладывает их к тегу;
3. **проверить ассеты**: `gh release view v0.1.0 --json tagName,assets` —
   там должен быть STL на каждый чехол из `CASES` и zip со всеми сразу.

Если репозиторий новый, а релизный PR не появляется: в настройках должно
стоять Settings → Actions → General → **Allow GitHub Actions to create and
approve pull requests**.

### Известная заминка

CI на самих релизных PR иногда падает, не запустив ни одного джоба, — GitHub
пишет «likely failed because of a workflow file issue». Это не наша поломка:
`gh run rerun <id>` на том же коммите проходит зелёным. Блокировать релиз
этим не нужно.

## Что гоняет CI

`.github/workflows/ci.yml`: pre-commit целиком, pytest на трёх версиях Python
и сборка чехлов. Ставить на раннер нечего — булевы операции считает
manifold3d из зависимостей, превью рисует свой растеризатор. Превью
рендерится в каждой сборке и прикладывается к прогону: на картинках видно
то, чего не поймает ни один замер.

## Проверка своей работы

Перед тем как звать ревью:

1. `uv run pytest` — геометрия сошлась;
2. `make preview` и посмотреть три ракурса **глазами**;
3. если правка меняет посадку чехла (полость, толщина стенки) — сказать
   об этом прямо и предложить напечатать пробу до серии.

Ревью в этом репозитории особенно внимательно к трём вещам: цифры отступов,
совпадение параметров модели с тестами и то, что в коммит не попали
собранные артефакты.
